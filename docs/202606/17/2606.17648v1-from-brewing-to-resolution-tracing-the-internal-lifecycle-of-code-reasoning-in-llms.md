## 摘要
标准准确率指标无法解释为什么LLM能处理变量追踪，却在语义等价的循环上失败。我们研究了代码推理的内部生命周期：模型首先酝酿答案，使其在很多层之前就能线性可恢复，但尚不能自我解码；随后分化为四种解决结果之一：已解决、过度处理、错误解决或未解决。理解这一生命周期很重要，因为相似的任务准确率可能掩盖表面评估无法检测的根本不同的失败模式。我们引入了一种双重诊断框架，将逐层线性探测与上下文剥离解码（CSD）相结合，并将其应用于跨越Qwen、Llama和DeepSeek架构的16个模型的六个代码推理任务族。每个任务族中所有四种结果都占据重要比重：总体已解决率仅为41.5%，多个任务低于30%。对结构、深度和操作符的控制实验揭示了任务特定的失败瓶颈：函数调用已解决率从61.1%骤降至2.5%（当调用深度从一层增至三层时）。在不同的架构和规模下，酝酿框架保持稳定，所有16个模型的标准化酝酿时长在24-42%之间，而解决成功率随能力变化。这表明该框架是所测试的仅解码器Transformer家族中稳定的经验规律，而解决成功率与能力、规模和训练协变。代码：https://github.com/euyis1019/llm-brewing

## Abstract
Standard accuracy metrics cannot explain why LLMs handle variable tracking but fail on semantically equivalent loops. We study an internal lifecycle of code reasoning in which models first brew the answer, making it linearly recoverable many layers before it becomes self-decodable, and then diverge into one of four resolution outcomes: Resolved, Overprocessed, Misresolved, or Unresolved. Understanding this lifecycle matters because similar task accuracies can mask fundamentally different failure modes that surface-level evaluation cannot detect. We introduce a dual diagnostic framework pairing layer-wise linear probing with Context-Stripped Decoding (CSD) and apply it to six code-reasoning task families across 16 models spanning Qwen, Llama, and DeepSeek architectures. All four outcomes carry substantial mass in every task family: overall Resolved is only 41.5%, with multiple tasks below 30%. Controlled sweeps over structure, depth, and operators expose task-specific failure bottlenecks: Function Call Resolved plunges from 61.1% to 2.5% as call depth increases from one to three. Across architectures and scales, the brewing scaffold remains stable, with normalized brewing duration 24-42% across all 16 models, while resolution success varies with capability. This indicates that the scaffold is a stable empirical regularity across the tested decoder-only Transformer families, whereas resolution success covaries with capability, scale, and training. - **研究动机**：当前的标准准确率指标无法解释LLM在代码推理任务中的内部差异。例如，一个模型可能轻松追踪变量赋值，但在处理算术运算时变得脆弱；能处理显式循环，却在语义等价的展开序列上表现挣扎。这种“谜一样的不一致性”表明，仅仅观察最终正确率会掩盖模型内部根本不同的失败模式。

### 2. 方法论

- **核心思想**：论文提出了一个**双诊断框架**，通过两个视角来追踪代码推理的内部生命周期：
    1.  **信息可用性 (Availability)**：指答案信息是否已在某个层的隐藏状态中被线性可读地编码。
    2.  **信息就绪性 (Readiness)**：指模型自身的解码流水线是否能在不依赖原始上下文的情况下，从该层的表示中解码出正确答案。
- **关键技术细节**：
    - **双诊断框架**: 包括两个诊断函数：
        1.  **逐层线性探测 (Linear Probing, Φ_P)**：在每个Transformer层，训练一个逻辑回归分类器来检查该层的隐藏状态是否线性可分地包含正确答案。这用于衡量**信息可用性**。
        2.  **上下文剥离解码 (Context-Stripped Decoding, CSD, Φ_C)**：从源输入中提取某层的隐藏状态，并将其注入到一个仅包含问题后缀（去除了代码上下文）的目标提示中。接着，让模型从该层继续前向传播并生成输出，通过基线logit减法来隔离注入表示对输出的贡献。这用于衡量**信息就绪性**。
    - **生命周期与结果分类**：
        - **酝酿 (Brewing)**：定义了两个关键节点：**首次探测正确层 (FPCL)**，即线性探测首次正确预测答案的层；**首次联合正确层 (FJC)**，即线性探测和CSD同时正确预测答案的层。
        - **酝酿区间 [FPCL, FJC)**：模型内部，答案信息已存在但尚未就绪的短暂处理阶段。
        - **四个最终结果**：根据FJC是否存在、最终输出正确性以及尾部窗口的CSD置信度，将每个样本的轨迹分类为：
            - **已解决 (Resolved)**：存在FJC且最终输出正确。
            - **过度处理 (Overprocessed)**：存在FJC，但最终输出错误（即模型早期形成了正确答案，但后续处理破坏了它）。
            - **错误解决 (Misresolved)**：不存在FJC，但模型对某个错误答案表现出高置信度。
            - **未解决 (Unresolved)**：不存在FJC，且尾部置信度低，模型未能完成计算。
- **因果验证**：通过三项因果干预实验验证了上述分类的真实性：
    - **FJC层激活修补**: 修补FJC层的状态到中性提示，答案翻转率显著高于周围层，证明FJC是因果上的关键节点。
    - **对过度处理样本跳层**: 跳跃FJC后的层，直接利用FJC层的表示解码（通过alpha混合注入），可以挽救约47.8%的过度处理样本。
    - **对未解决样本重注入**: 将FPCL层的表示重新注入到模型尾部，可以挽救22-38%的未解决样本。

    - 数据流：值追踪 (Value Tracking)、计算 (Computing)
    - 控制流：条件分支 (Conditional)
    - 数据+控制流：函数调用 (Function Call)、循环 (Loop)、循环展开 (Loop-unrolled)
- **Benchmark特点**：每个任务的答案始终是单数字（0-9），这使得诊断空间统一。每个任务族包含27种难度配置（3个难度维度各3个等级），生成了大量可控的代码片段。
- **对比方法**：论文将提出的框架应用于**16个不同的仅解码器Transformer模型**，包括Qwen2.5-Coder、Qwen2.5-Base、Qwen3-Base、DeepSeek-Coder、CodeLlama和Llama-2系列，规模从0.5B到14B参数不等，以评估框架的通用性和模型差异。

### 5. 实验数量与充分性

- **实验数量庞大**：每个模型在6个任务族上测试，每个任务族4,050个样本（150样本 × 27配置），总计每个模型24,300个样本，16个模型共生成372,600个样本的诊断数据。
- **实验充分性较高**：
    - **广泛覆盖**：实验覆盖了多个主流模型家族和不同规模，增强了结论的泛化性。
    - **控制变量**：通过精细的难度维度（深度、操作符、结构等）的扫掠，系统性地研究了特定代码原语（如函数调用深度）对失败模式的影响。
    - **因果验证**：通过三种不同的因果干预实验，验证了所提出分类（如过度处理、未解决）不仅仅是相关性的，而是具有因果结构。
    - **公平性**：对比都是在同一基准、同一诊断框架下进行，模型之间的比较是客观公平的。

### 6. 主要结论与发现

1.  **揭示内部生命周期**：代码推理在模型内部遵循一个“酝酿到解决”的结构化生命周期。答案信息先在早期层变得**可用**（线性可读），然后经过一个约占总深度38%的“酝酿区间”，最终才变得**就绪**（模型自身可解码）。
2.  **四个具有因果基础的结果**：所有样本的轨迹最终分化为四种结果：已解决（41.5%）、过度处理（26.4%）、错误解决（8.5%）、未解决（23.7%）。这些类别通过因果干预被证实是真实的计算状态。
3.  **任务特定的失败瓶颈**：不同代码原语触发截然不同的失败模式。例如，函数调用深度从1增加到3，解决率从61.1%暴跌至2.5%，这是最严重的瓶颈；而计算任务的关键问题是过度处理（内部计算不稳定）。
4.  **酝酿框架稳定，能力随尺度变化**：“酝酿”这个结构在所有16个测试模型中稳定存在（标准化时长在24-42%之间），表明它是仅解码器Transformer中的一个**稳定的经验规律**。然而，最终的解决成功率则与模型的能力、规模和预训练数据质量相关，是一个**能力指标**。
5.  **与外部基准一致**：该框架揭示的能力排序（如更大型号、代码专用模型表现更好）在外部CRUXEval-O基准上也得到了复现，验证了研究结果的有效性。

### 7. 优点

- **方法创新**：框架创新性地将“信息可用性”与“信息就绪性”分离，通过配对探测和CSD，揭示了传统准确率无法捕捉的深层动态过程。这比简单地观察logit lens或探测更深入。
- **细致的因果分析**：不仅提出了分类，还通过三种不同的因果干预实验（修补、跳层、重注入）提供了坚实的因果证据，证明这些类别确实对应于不同的计算状态。
- **发现切实可行的失败模式**：识别出“过度处理”和“未解决”这两个对立的失败模式。前者需要提前退出，后者需要更多计算，这为设计自适应推理策略（如动态深度）提供了直接指导。
- **广泛的实验验证**：在16个多种架构和规模的模型上进行验证，增强了结论的普遍性，并明确区分了稳定机制（酝酿）与变化能力（解决成功）。

### 8. 不足与局限

- **分析粒度较粗**：论文的诊断是在整个层粒度上进行的，无法精确定位具体的注意力头或MLP子层是如何驱动酝酿到解决的过渡。更精度的路径修补（path patching）是自然的下一步。
- **基准的局限性**：使用的CUE-Bench是短小、单原语的合成程序。论文提出的内部动态在更复杂、多语句的、现实的代码组成中是否保持一致，是一个悬而未决的开放问题。
- **解释的局限性**：论文坦诚地指出，他们发现了“酝酿”这个稳定规律，但并未提供一个可证明的电路级解释。不同模型家族中负责“重写”答案的组件（注意力vs MLP）各不相同，表明这一规律是经验性的，而非普遍真理。
- **未解决的可扩展性问题**：虽然论文提出了无需真实标签的检测信号，并获得了不错的AUC，但将其扩展到现实世界的、多token代码生成场景的实用性仍是一个挑战。
- **潜在偏差风险**：基准的答案分布并非完全均匀，部分任务（如条件分支）倾向0/1数字，这可能在极少数情况下引入微小偏差，尽管论文已通过约束生成和诊断设计将其影响降至最低。
